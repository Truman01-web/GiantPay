## Confirmed findings and implementation

| Attack path or defect | Correction and evidence |
| --- | --- |
| A script on the allowed merchant origin could read staff GET endpoints using a staff cookie: global CORS accepted both portal origins and read routes did not enforce the staff origin. | Staff route prefixes now require the exact staff origin when Origin is supplied. Merchant and staff session authenticators also enforce their respective origin. Regression requests include a valid staff session with the merchant Origin. Browser acceptance attempts the read from the actual merchant portal and expects 403 while the staff session remains usable. Missing Origin remains supported for non-browser clients; credential-bearing browser mutations still require exact Origin and CSRF. |
| Any Authorization header disabled cookie CSRF checks globally, including routes that authenticate through cookies. | Cookie-bearing mutations always undergo their context-specific CSRF check. An invalid Bearer header plus a merchant cookie cannot bypass it. Byte lengths are compared before timingSafeEqual, preventing malformed UTF-8 tokens from producing a 500. |
| Merchant recovery accepted STAFF login challenges and could consume a staff recovery credential through the wrong portal. | Recovery requires MERCHANT context and a merchant-bound user. The database regression verifies that both staff challenge and recovery code remain unused after rejection. This is a context-confusion defect; existing merchant authentication rejected the resulting null-merchant session, so a successful merchant privilege escalation was not established. |
| Merchant TOTP verification used unqualified FOR UPDATE with nullable outer joins, which PostgreSQL rejects. It also did not require a verified enrollment. | Lock only challenge, user and enrollment rows; require verified_at. Real-route merchant TOTP verification and replay rejection pass against PostgreSQL. |
| MFA login and recovery ignored shorter configured session TTL/absolute limits, using fixed 12/24-hour values. | Merchant TOTP, merchant recovery and staff MFA apply configured limits to both database expiry and cookie lifetime. Tests configure a two-hour TTL with a one-hour absolute cap and assert the database and cookie are capped at one hour. Concurrent recovery attempts produce exactly one success. |
| Password reset revoked sessions but left outstanding login/enrollment challenges usable. | Consume all unused authentication challenges for the user inside the reset transaction. A pre-reset staff login challenge is invalidated by a real reset request. |
| Staff enrollment and enrollment-code verification lacked dedicated challenge/IP throttles. | Both endpoints now enforce independent IP and challenge limits. Regressions rotate source IPs and prove the sixth attempt against the same challenge is rejected. Existing identity key canonicalization already handled email case variants; an additional regression preserves that behavior. |
| Outgoing merchant webhook delivery validated DNS and then let fetch resolve the hostname again, permitting DNS rebinding between validation and connection. Its timeout ended at response headers. | A native HTTP(S) transport validates every socket DNS answer, rejects mixed private/public answers, disables socket pooling and does not follow redirects. The original hostname remains available for TLS certificate validation. The existing abort deadline now covers the bounded response body. Injected DNS/request regressions cover private and mapped addresses, mixed answers, guarded socket options, 204 responses, oversized bodies and redirects without real network delivery. |
| Default request URL logging could retain checkout capability tokens and reset/query credentials; database error details could retain submitted values. | Redact req.url and database error detail/query/parameters in addition to existing cookie, authorization and secret redaction. Routing remains available through bounded route metrics and requests can be correlated by request ID. |
| Dependency audit found known vulnerabilities in application and build/test dependencies. | Update Fastify, Zod, Vite, Vitest and coverage packages, with scoped overrides for affected transitive dependencies. The resolved 704-dependency audit reports zero known advisories. CI now rejects advisories at low or higher severity. Node engines match the updated Vitest support range (22.12+, supported even release lines). Thread workers avoid a locally reproduced Windows fork startup stall without disabling test isolation or integration enforcement. |

## Other paths traced

- **Tenant isolation and permissions:** merchant sessions require a non-null merchant, active user, MERCHANT session context, expiry, idle limit and no revocation. Staff sessions require STAFF context, verified MFA, provisioned platform role, exact staff email domain and permissions. Resource queries bind the authenticated tenant; API keys remain restricted by scopes and browser-only endpoints reject them. Existing team, ledger and private-evidence integration tests exercise cross-tenant and permission failures. No new tenant escape was confirmed in the paths reviewed.
- **Reset, OTP and MFA:** reset tokens are hashed, bounded and consumed transactionally; sessions are revoked. Registration OTPs use keyed digests, attempt limits, resend invalidation and generic existing-account responses. TOTP counters prevent replay and recovery codes are hashed and consumed under locks. Reset and enrollment delivery are tested synthetically; no email was sent.
- **CORS, cookies, proxies and limits:** origins use exact equality, secure cookies are enforced in production, session cookies are HttpOnly and portal-specific, and mutations require context-specific CSRF. Forwarded client identity is honored only from configured proxies. Redis-backed limits use atomic counters and fail closed on security-store failure. Browser cookies remain host-scoped, so origin separation must continue to be enforced server-side.
- **Flutterwave:** v3 verif-hash authenticates notifications; authoritative server verification checks transaction ID, exact minor-unit amount, currency and generated reference before crediting. A sandbox callback cannot credit a Flutterwave payment. Failed/unavailable/mismatched verification does not credit the ledger. The v3 contract must not be confused with newer webhook signature contracts.
- **Ambiguity and concurrency:** durable intent and retry receipt precede provider I/O. Reusing a key does not resubmit an uncertain charge; changed payloads conflict. Payment/source locks, unique provider transaction binding, replay receipts and immutable balanced journals prevent duplicate credit. QR capacity includes uncertain reservations. Existing database regressions cover initiation ambiguity, same-key and different-key concurrency, late callback races and conflicting verified IDs.
- **QR and redirects:** public QR responses select display fields and limits rather than returning a database row, customer records or private credentials. Fixed amounts are authoritative; customer-entered values are bounded; expiry and capacity are rechecked while reserving under lock. Hosted provider URLs require the exact HTTPS provider host and frontend response validation. Merchant redirectUrl is stored/displayed as text and is currently not executed; enabling that unfinished feature requires an explicit safe redirect policy. No current script-execution path through that field was found.
- **Uploads and downloads:** binary evidence is limited to 10 MiB with matching extension/type/signature and safe filenames, held in quarantine until a CLEAN scanner verdict, stored privately with authenticated encryption and fetched through tenant/permission checks. Downloads require clean state and digest/size validation and use attachment, nosniff and private/no-store headers. Missing storage/scanner adapters fail closed with 503. Synthetic adapters do not establish production malware detection or storage configuration.
- **Errors and secrets:** unexpected API failures use generic responses with request IDs; credential patterns and generated artifacts must not be staged. Dependency caches, local service scripts, reports, logs, environment files and builds are excluded from this change.

## Remaining risks and external acceptance

This review supports the sandbox implementation, not production payment activation. Actual Flutterwave account approval, provider sandbox credentials/acceptance and Malawi channel availability remain unverified. Refund execution, bank integrations and unattended provider recovery/reconciliation remain incomplete. An uncertain intent deliberately stays PROCESSING and reserves capacity until authoritative evidence or operator reconciliation. Manual recovery procedures and monitoring are required before broader use.

Real SMTP, production private storage, malware scanner effectiveness, reverse-proxy configuration, DNS/egress policy and hosted cookie/TLS behavior were not exercised. Preserve network egress restrictions as a second boundary for merchant webhook delivery. The tests cover identified attack paths and are not an exhaustive penetration test or a guarantee about unreviewed paths. Review and green CI on this security PR, plus resolution of its unmerged PR #26 dependency, are required before merge consideration. No merge or deployment is authorized here.
